## 1. EXECUTIVE SUMMARY

Task GAP-004 establishes the canonical Source of Truth & Conflict Resolution Matrix for the AI Business Operating System (AI BOS). In a multi-tenant, AI-assisted operating system, multiple sources of information—such as database facts, business configurations, approved knowledge base items, real-time caches, conversation context, AI memory, customer claims, and external provider webhooks—frequently intersect.

The core objective of GAP-004 is to define deterministically and auditably:
1. Which source is the **Official Source** (contractual truth) versus **Read Source** or **Derived Source** for every data domain.
2. Who holds **Write Authority** and what official **Update Path** must be followed.
3. How conflicts between competing sources (e.g., AI memory vs. DB stock, payment provider status vs. customer statement, approved knowledge vs. live transaction state) are resolved deterministically without guessing or AI hallucination.
4. When system processing must fail-safe, halt, or escalate to Human Platform Owner / Tenant Owner.

This document bridges the locked architectural baseline (Q1–Q51 / ACT-001–410) with the actual repository implementation in `app/`, `frontend/`, and `migrations/`. It enforces the foundational principle: **"DATABASE = FACTS, AI = REASONING."**

## 3. SOURCE HIERARCHY

When two or more information sources present conflicting data, AI BOS resolves the conflict strictly according to the following canonical 8-tier hierarchy:

1. **Tier 1: Q1–Q51 / Locked Architectural Decisions (ACT-001–410)**
   - Highest authority. Defines system invariants, actor boundaries, and immutable rules.
2. **Tier 2: Master Blueprint v1.1**
   - Canonical product vision, system boundaries, and architectural design principles.
3. **Tier 3: Master Reference / Master Execution Plan v1.1**
   - Standard execution roadmap and dependency ordering.
4. **Tier 4: Discovery Notes**
   - Contextual design agreements and preliminary findings.
5. **Tier 5: Future Decisions / Backlog**
   - Approved future direction (DEFERRED/FUTURE status).
6. **Tier 6: Operational Flow & System Runtime Rules**
   - Real-time business rule engine logic and deterministic state machine transitions.
7. **Tier 7: Repository Implementation (`app/`, `migrations/`)**
   - Technical evidence of current software behavior. *Note: Repository code is evidence of technical state, NOT an automatic product requirement if it contradicts higher tiers.*
8. **Tier 8: Implementation History / Previous PR Material**
   - Historical context and past change logs.

**Conflict Rule:** If a higher-tier source contradicts a lower-tier source or repository implementation, the higher-tier source governs and the discrepancy is flagged as `CONFLICT` or `POTENTIAL ERROR`. Lower-tier sources must NEVER override higher-tier canonical decisions.

## 4. DEFINITIONS

- **Official Source (Source of Truth):** The single database entity or authoritative system contractually recognized as absolute fact (e.g., PostgreSQL `products` table for catalog prices).
- **Read Source:** The data store or cache read by the application or AI at runtime (e.g., Redis cache or assembled prompt context).
- **Derived Source:** Data generated by calculation, aggregation, caching, or AI interpretation (e.g., analytics reports, conversation summaries, extracted AI memory). Derived sources are strictly non-authoritative.
- **Write Authority:** The authenticated actor, system component, or verified webhook permitted to mutate the Official Source.
- **External Provider State:** State reported by external APIs (e.g., Midtrans payment status, WhatsApp delivery status). Must pass verification before updating Internal Authoritative State.
- **Internal Authoritative State:** Reconciled internal database record representing verified transactional reality.

### Case 1: Product DB vs. AI Knowledge vs. Cache
- **1. Domain:** Business
- **2. Sub-domain / Data:** Product Information & Metadata
- **3. Business Purpose:** Provide accurate product details to customers and sales agents.
- **4. Official Source:** `products` DB table (`app/database/models/product.py`).
- **5. Read Source:** DB / `ProductRepository` (`app/repositories/domain.py`).
- **6. Write Authority:** Business Owner / Admin / Approved Change Request.
- **7. Update Path:** `PUT /api/v1/products/{id}` or Change Request Approval -> DB commit.
- **8. Freshness Requirement:** Real-time.
- **9. Version Requirement:** Timestamp (`updated_at`).
- **10. Conflict Source A:** Official DB `products` table.
- **11. Conflict Source B:** Stale AI Knowledge Base item or cached product response.
- **12. Conflict Type:** Data Inconsistency / Stale Data.
- **13. Resolution Rule:** **DB Wins.** DB facts strictly override AI knowledge or cache (ACT-047). Context Assembly invalidates stale knowledge when DB facts are assembled.
- **14. Escalation Rule:** If DB product is marked `is_active=False` or deleted, AI must state product is unavailable.
- **15. Failure Behavior:** Fallback to explicit DB product fields; log cache mismatch.
- **16. UNKNOWN Behavior:** If product is missing from DB, return product unavailable (ACT-050).
- **17. Audit Requirement:** Log business data query and context assembly source.
- **18. Tenant Scope:** Strictly tenant-isolated (`tenant_id`).
- **19. Permission:** `products.read` for reading, `products.write` for mutating.
- **20. Authority:** Tenant Owner / Admin.
- **21. Risk:** MEDIUM.
- **22. Existing Implementation:** Implemented in `app/core/context_assembly/service.py` and `app/repositories/domain.py`.
- **23. Evidence:** `ContextAssemblyService._assemble_facts` queries `ProductRepository` directly.
- **24. Status:** `PASS`.
- **25. Open Question:** None.
- **26. Verification Evidence:** Tested via `tests/test_gap_004_source_of_truth_matrix.py::test_cross_tenant_product_repository_isolation`.

## 8. TENANT ISOLATION ANALYSIS

Every official source across all 6 domains is strictly bound to a `tenant_id` foreign key referencing the `tenants` table (`app/database/models/tenant.py`).

2. **Repository Filter Enforcement:** All domain repositories in `app/repositories/domain.py` explicitly filter queries using `where(Model.tenant_id == tenant_id)`.

5. **Cache & Memory Isolation:** Redis keys and memory models embed `tenant_id` in their prefix/filters (`client_memories.tenant_id`, `business_memories.tenant_id`). Cross-tenant memory retrieval is strictly impossible.

## 9. AI MEMORY BOUNDARY

AI Memory (`client_memories`, `business_memories`) provides conversational context and long-term personalization. However, under ACT-088 and ACT-309, AI Memory is classified as a **Derived / Non-Authoritative Context Source**.

### Enforced Rules:
1. **No Operational Override:** AI Memory CANNOT alter DB product prices, stock, payment status, subscription status, or permissions.
2. **Fact Primacy:** In `ContextAssemblyService`, authoritative DB facts (`facts`, `business_profile`) are assembled at the top of prompt context. Optional client memory is placed at lower priority and trimmed first under the 16 KB context budget (`MAX_TOTAL_CONTEXT_BYTES=16384`).
3. **Explicit Statement Priority:** An explicit current customer statement overrides older stored memory (ACT-088).
4. **Memory Governance:** Memory carries `confidence`, `status`, `source`, `version`, and `expires_at`. Low-confidence memory (`status='INFERRED'`) cannot drive sensitive operations.

---

## 10. PAYMENT / TRANSACTION TRUTH BOUNDARY

Financial and checkout state integrity is governed by strict deterministic gates:
1. **Customer Claim vs. Payment Truth:** A customer statement in chat ("I transferred Rp 500.000") or a screenshot upload is treated as an unverified claim (ACT-108, ACT-286). It does NOT update `payment.status` or `order.status` to `PAID`.
2. **Authoritative Webhook Flow:** Payment status transitions to `SUCCESS`/`PAID` strictly when `PaymentService.handle_provider_webhook` receives a valid provider webhook matching:
   - Valid provider HMAC signature (`X-Hub-Signature` / Midtrans key).
   - Exact invoice amount and currency match.
   - Row-level lock (`with_for_update()`) on target payment record.
3. **Price Snapshot at Checkout:** When an order is created, `OrderRepository.create_order_with_items` snapshots `unit_price` on `order_items.unit_price`. Subsequent catalog price changes do not alter historical order line item prices (ACT-053, ACT-103).
4. **Stock Revalidation:** Volatile inventory is revalidated and deducted atomically inside transaction boundary with row locking (`select(...).with_for_update()`) (ACT-054, ACT-104). Check constraints (`check_product_stock_non_negative`) enforce zero-overselling at SQL level.

---

## 11. KNOWLEDGE VS. LIVE STATE BOUNDARY

Knowledge Base items (`knowledge_items`) represent approved business policies, FAQs, and SOPs.
1. **Policy Source vs. Transactional Fact:** Knowledge items provide textual explanations (e.g., return window policy or general pricing description). They do NOT represent live transactional state.
2. **Conflict Resolution:** If an approved FAQ text contradicts live DB product data (e.g., FAQ says "Hoodie is Rp 200k", but DB `products.price` is Rp 250k), the **Live DB Product Price Wins** (ACT-047, ACT-057).
3. **Knowledge Expiry:** Knowledge items marked `OUTDATED` or `ARCHIVED` are excluded from active context assembly (ACT-080).
